# 克制与工作流（第 13 章 Better Living with Patterns）

这份文件管三件事：**怎么读一个模式条目、什么时候才允许自己引入模式、引入了怎么留档**。
SKILL.md 的四步判定不够用时（比如评审别人的设计、或者自己开始"手痒想抽象"），回到这里。

## 什么才配叫模式（三条测试，缺一不算）

1. **复发**：是反复出现的情境，不是这次的临时补丁（书里"砸车窗"的例子就只配当一次性招数）。
2. **可迁移**：足够通用，别的开发者在自己的代码里也能用；只对你这个模块成立的写法是你的局部约定，不是模式。
3. **有名**：有名字才进得了共享词汇。给自己造的东西起名前先过前两条。

推论：**模式是被发现的，不是被发明的**；Rule of Three（同一形状在自己代码里第三次出现，才有资格抽象成"模式"）（第 13 章）。
想"发明一个模式"之前先读目录——大多数新想法是已知模式的变体。

## 怎么读目录条目（顺序不能跳）

`Intent → Motivation → Applicability` 判**合不合**；`Consequences` 判**付不付得起**；
`Structure / Participants / Collaborations` 对**角色落到你哪个类上**；
`Implementation / Sample Code / Known Uses / Related Patterns` 才写代码。

- **跳过 Consequences 是副作用的主要来源**：只读"能干什么"就上模式，等于只看了收益栏的账单。
- **跳过 Related Patterns 会错过更省的那一个**：阶梯上的低档常常就在"相关模式"栏里。
- 书上的 Sample Code 是**教学代码**：不带健壮性、不带封装、没有包结构（原书前言明说"现实中不推荐这样"）。照抄示例类结构进生产代码是误用来源，不是模式本身的问题。

## 引入模式的六步闸（第 13 章 p594-595 原序）

1. 确认设计里有一个**真问题**（不是"看起来不够优雅"）。
2. 想一遍更简单的解法能不能行；能行就先用简单的。
3. 写下约束（性能、兼容、团队熟悉度、上线时间）。
4. 用 Intent / Applicability 把问题和候选对上。
5. 确认 Consequences 里的代价你**当下付得起**。
6. 检查它对设计其余部分的影响（调用方、测试、部署、新人上手），然后才动手。

5-6 没过不许提交。局部问题解决了、把污染推给调用方，是净亏。

**唯一允许的提前上模式**：能指名的变化——已在需求/roadmap 上的功能、已经存在的第二个平台或租户类型、反复被复制的同一条变化轴。
"万一以后要多租户"不算（第 13 章：实际变化 vs 假设变化）。

## 重构时间就是找模式的时间（第 13 章给的信号→模式映射）

| 重构时看到的 | 搬向 |
|---|---|
| 按类型/按状态的长条件分支 | State 或 Strategy |
| 散落在多个类里的具体实例化 | 工厂 + 组合根 |
| 类之间直接互调、牵一发动全身 | Observer / Mediator / Facade |
| 多个子类里重复的算法骨架 | Template Method |

两条限制：重构必须**保持行为**，不许拿"上模式"当改变语义的掩护；没理由碰的代码不重构。

## 撤掉模式的合法性（第 13 章原文授权）

"把不真的需要的东西拿掉"是正当维护动作：灵活性没人用、系统已经变复杂 → 收回成简单设计。
触发形状：死扩展点、只有一个实现的接口、没人组合的装饰栈、只有一个产品的工厂。
两条边界：不要因为模式名神圣就供着它；也不要撤掉已知即将到来的变化所需要的那层弹性。

## 成本/收益账本（每次上模式前摊开）

- 收益：验证过的解法、可文档化的设计、共享词汇带来的沟通加速。
- 代价：更多类和对象、更多间接层、更高理解成本、有时是可测的性能下降。
- **只算收益就是没算**。原则级解法（封装变化、针对超类型、组合）能达到同一结果时，付零成本的那条。

## 工具箱顺序（颠倒了就是模式驱动设计）

OO 基础 → 设计原则 → 模式 →（更宽的）架构模式。
拿这个顺序自查三种状态（第 13 章 "Your Mind on Patterns"）：

- 初学者：到处看见模式，越多越好（"Hello World 也要用模式"——第 1 章把这叫 Pattern Fever）。
- 中级：开始看出合与不合，仍会把方的塞进圆的，开始改结构。
- 熟手：只在合适处长出来，偏好最简解，能分清形近模式的**意图**差别，并且仍然自称初学者。

自查方法：**数你用的模式数，再数你实际解决的问题数**，前者明显大于后者就是在倒退。

## 反模式卡（怎么写、写什么）

反模式 = 一个**诱人**的坏解法。一张卡必须有四件：为什么它吸引人、长期怎么伤你、改用哪个模式、给它起个名字。
只写"不许这样"、不给替代清单会被无视。

- **Golden Hammer（手里只有锤子）**：用熟悉的那一招去套不合的问题；每个新需求都交给同一个最爱（单例、某个框架、某个模式族）。
  吸引点在"心里有底、好估工、团队熟"，这些是真力量，但不构成适配。解法是扩知识面和评审时强制列替代。
- **假设性通用化（speculative generality）**：为想象中的变化搭架构，句式是"万一需要""以后要扩展""为了面向未来"。代价是永久的额外类和更慢的理解，而那个需求常常不来。
- **模式驱动设计（pattern-first）**：能报出模式名但说不出它这次要吸收哪一处具体变化。第 12 章把它列为该章头号反模式（一个"统计调用次数"的需求被堆上抽象工厂 + 装饰者 + 观察者，其中好几个是纯多余）。
- **分析瘫痪 / 模式堆塌**：这两条**不在本书**（全文 grep 无命中），是通用工程说法——研究目录代替做决定；一次迭代给一个模块堆进好几个新抽象却没有对应新需求。
  解法：限定研究时长 → 选过得了六步闸的最简候选 → 原型 → 靠重构继续学；一次只解决一个已验证的问题，加完就停。

## 留档：决策记录写在哪、写什么

- 记在**代码旁边**：`docs/adr/NNN-*.md` 或模块 README 的一节；类名和注释里保留模式名。（"记在没人看的 wiki"等于没记。）
- 一条记录必须含：模式名+类别+作用域（class/object）、**本仓库里的具体问题**、力量（目标 vs 约束）、采用的形态与**偏离教科书之处**、否决的备选及原因、接受的代价、关联模式、撤销条件与复查日期。模板见 SKILL.md。
- 偏离教科书是**允许的并且要写明**：复用想法，不是复用形状；Gamma 原话的精神是"工具不是规则"（第 13 章）。真实代码里几乎不会碰到和目录图一模一样、未经改形的用法。
- 别给"只有一个类的平凡抽象"写模式记录——那条记录本身在夸大设计。

## 共享词汇的五个兑现场合（第 13 章）

设计会议、开发者之间讨论、架构文档、代码注释与命名、给有兴趣的人讲解。
混合听众时补一行 intent，否则名字对读不出引用的人等于零信息。

## 模式在野（读代码比背目录有用）

框架内部、GUI 事件链、MVC 与多层应用、并发库、UI / 业务流程 / 组织模式集。
两个坑：带领域标签不等于经典解法适用；**架构级模式名与对象级模式名不要混写进同一条决策记录**（层级不同，判据不同）。

## 关于 ADAPT（**非本书**）

全书 grep 无 "ADAPT" 字样，本节是我加的过渡工具，只用于"已经决定要重构"之后给方向，不作为引入模式的理由：

- **A**dd a new abstraction：调用方点名了具体实现、第二个实现正要来、测试需要一个缝 → 引一个协议/接口。只有一个可能实现且没有变化轴时不做。
- **D**elegate to other objects：某个方法其实是可插拔策略，或类在自己字段上长出了 switch → 搬给协作者，靠组合而不是靠子类变。琐碎胶水不搬。
- **A**dapt to new interface：一侧接口你不能改、边界处签名或词汇对不上 → 适配器/facade。接口本来就对得上时别造透传壳。
- **P**reempt change with patterns：roadmap 上点名的变化 → 只在它会落地的那一处放缝，并写进决策记录。说不清具体变化的不算预防，叫赌博。
- **S**eparate concerns：一个类因多个不相关理由被改 → 按"变化理由"切开，每个轴一个归属。只把行挪来挪去不算分离，算 churn。
